# MLB The Show 26 (`0100AA7024094000`)

<!-- PEANUTS: a Peanuts Native profile and note (Banana Native has none for this title). -->

Update 1.0.19 (v1245184) on base v65536. SDK 19.3.11. San Diego Studio's own engine with NVN graphics. Modules `main` and `sdk` only: no `subsdk`, and `main` imports `nn::ro` but the RomFS holds no `.nro` or `.nrr` files.

**Status (current): provisional profile; the first boot stopped in `nninitStartup` (resolved by `mem_used`, not yet rerun).** The survey, the provisional profile, the shader split and the pack ran on a PC (Linux under WSL) from a `.nup` of the merged base and update; the test app came from `.github/workflows/test-apk.yml`. The aim is the offline modes (Road to the Show, exhibition); the online modes need Sony's servers and are out of scope. The game imports `nn::socket`, `nn::ec`, `nn::friends`, `nn::account` and `nn::nifm` for them.

## Files and shaders

- RomFS: 86,057 files, 35.20 GB. Platform folders `NSW/`, `CROSS/`, `AND/`, `PS4/`, `FLUX/` at the top. Most files are `.tex` (38,014) and `.mod` (25,940).
- **Shaders: GLSLC outputs in `.fxbnvn` files.** `NSW/SHADERS` holds 456 `.fxbnvn` files (161.7 MB, 56 bytes to 2.1 MB). Each starts with `FXB\0`, then its own length and a header length; inside are whole GLSLC outputs (magic `0x19866891`), each with one control section (`0x98761234`, 0x880 bytes) and its code area right after it. 7,720 outputs over all files (7,234 graphics, 486 compute), nothing compressed and no BNSH. 3-file banks of 56 bytes hold no shader. The survey's note ("no BNSH / BAHS at the top level … must be located first") does not count GLSLC outputs; `shader_split.py` reads them through its loose-file GLSLC path (`scan_whole` → `glslc_shaders`) with no new reader. `dm/tools/fxbnvn_probe.py` prints this structure from a `.nup` without writing game data.
- `shader_split.py` found 3,445 shaders: 244 compute, 1,757 pixel, 1,444 vertex, all from `nsw` (the 7,720 outputs repeat across banks). 5,776 variation pairs, 244 compute answer rows, no `[RED]` line. Single-stage programs: the 1,444 vertex shaders are paired with a cover of 4 pixel shaders.

## Memory

- Modules: 0x5a00000 (90 MB) after the rewrite. With the default 64 MB of used memory, `main` asked for a 0xc9400000 heap (pool − 64 MB) and `SetHeapSize` refused it. With `mem_used 0x6000000` it asks for 0xc7500000 (3.11 GB). Not measured in play yet.

## Found on this game

- **Heap sized from the application pool less used memory (resolved).** First boot on an AYN Thor (system driver and Turnip Gen8 V39, three runs): `[mem] SetHeapSize 0xc9400000 + modules 0x5a00000 > app pool 0xcd500000 (used memory reported 0x4000000 + bss 0)`, then `nn::diag abort: Result 0x1003` at `main+0x5b1b60` in `nninitStartup`, before any graphics. Fixed by `mem_used 0x6000000`. [Heap sized from the application pool less used memory](../../docs/reference/memory.md#heap-sized-from-the-application-pool-less-used-memory)

## Open

- SDK 19 (the survey's note: NVN object sizes and service layouts differ by SDK); other SDK 19 profiles exist ([OCTOPATH TRAVELER 0](../01005270232F2000/README.md)), so check against them first at bring-up.
- **Opening video: nsd (resolved).** At `ATT_SCREEN: FMV player init` the game connected to nsd:a and nsd:u itself and aborted (`Result 0xe8d`, `sdk+0x3f4cfc`, in `nn::nsd::GetApplicationServerEnvironmentType`, reached through `main`'s import `nn::oe::GetServerEnvironmentType`). The host answers that import with retail 0 (`hle_offline.c`); with it the opening video plays (0.2.11, both drivers).
- **Voice chat AudioOut used before it is opened (resolved).** COnline asks the headset output's channel count (`main+0x18cd30c`, `main+0x18cd674`) before the headset thread opens it; the host answers as for a closed output (`hle_audio.c`, `ao_or_closed`). 0.2.13 got past it on both drivers.
- **ContainsAudioOutBuffer (resolved).** The headset thread's null read at `sdk+0x1e7e24` right after `audio #2 Start`: the host takes over `nn::audio::ContainsAudioOutBuffer`. 0.2.14 reaches the menus, player creation and the first game.
- **3D scene black: 119 textures in one bind (resolved).** The game binds 119 texture handles in one call; the host refused binds of more than 32 whole and the 3D scene drew untextured. Recorded in parts of 32 (`hle_nvn.c`, `bind_handles`): 0.2.15 draws the stadium and players on Turnip.
- **Spikes, missing skin (resolved).** The skinning and player compute shaders (`SKINNINGCOMPUTE`, `PLAYERCOMPUTESHADERS`) write storage buffer textures at offsets off the device's texel buffer alignment (64); unbound, players drew as long spikes and the umpire's skin not at all. 0.2.18 copies such a binding into aligned scratch memory before the dispatch and back after it (`vka_draw.c` tbuf_view, tbuf_writeback): spikes gone, the umpire's face and the crowd draw.
- **Generated players' faces black (current).** Generated faces draw with `CAP_FACESHADER` (CAP: create-a-player; `ICE_FACESHADER` is the scanned faces'): in create-a-player its forward-lit variants cae2f651a34a6bce, bea07ae07db07982, 610e8ec87dbdade8. `DM_VK_TEX_STATS` on them (0.2.21): the face's own textures are fine (BC7 256x128 normal map and the BC1 skin colour, both GPU-encoded and taken since 0.2.20), but the irradiance cube it is lit by (16x16 B10G11R11, never GPU-written on the host) is all zero, as are an R8 1024x1024 and an RGBA8 128x64 input: a face lit by nothing, only its specular left. The game's image tools write cube maps through 2D array images of a storable format (`TEXTURECOPY`, `TEXTUREUTIL` compute: IMG dim 0x9), a texture of another target and format over the cube's storage. 0.2.22 widens the 0.2.20 take to any sampled texture with a GPU write through an uncompressed twin of its texel size and extent over its storage (`vka_tex.c` take_src; `storage take:` lines): rerun, every take was a BC one and the cube stayed zero, so it has no GPU twin over the same storage. `DM_VK_ZEROLOG` logged no zero image over data, so the cube's storage is empty when it is made. `tex_flush_upload` and `tex_dirty_upload` (0.2.23) changed nothing, so they are off again: the CPU does not fill it either. Its neighbour, a 16x16 RGBA16F cube with 5 levels, has data; the GPU likely makes the irradiance cube from it through a texture the host drops or places elsewhere. 0.2.24's `DM_VK_TEX_STATS` lines also give each input's storage, whether it holds data, and the live images and logged GPU writes over it (`vka_tex_id_storage`). The create-a-player model draws since 0.2.20 (its GPU-compressed textures had been all-zero, transparent blocks). Hair: root colour changes, tip colour does not, full beards do not draw. Also: the texel buffer view table filled a few minutes in (emptied when nearly full since 0.2.19); one texture ID past the image table (66224).
- Under Sudachi on Android with Turnip, generated players' faces draw black and some limbs draw in solid red, green, blue or white; worth comparing once this profile draws frames.
