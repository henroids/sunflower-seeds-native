# MLB The Show 26 (`0100AA7024094000`)

<!-- PEANUTS: a Peanuts Native profile and note (Banana Native has none for this title). -->

Update 1.0.19 (v1245184) on base v65536. SDK 19.3.11. San Diego Studio's own engine with NVN graphics. Modules `main` and `sdk` only: no `subsdk`, and `main` imports `nn::ro` but the RomFS holds no `.nro` or `.nrr` files.

**Status (current): plays on an AYN Thor (Turnip Gen8 V39): menus, Road to the Show (including create-a-player and a loaded career), exhibitions with real teams.** Skin, faces, hair colours and beards of generated players render since 1.0.24 (see [the skin and hair write-up](../../../docs/mlb-the-show-26-skin-and-hair.md)). The pack is made on a PC (Linux under WSL) from a `.nup` of the merged base and update; the apps come from `.github/workflows/test-apk.yml` (test) and `release-apk.yml` (official). The aim is the offline modes (Road to the Show, exhibition); the online modes need Sony's servers and are out of scope. The game imports `nn::socket`, `nn::ec`, `nn::friends`, `nn::account` and `nn::nifm` for them.

## Files and shaders

- RomFS: 86,057 files, 35.20 GB. Platform folders `NSW/`, `CROSS/`, `AND/`, `PS4/`, `FLUX/` at the top. Most files are `.tex` (38,014) and `.mod` (25,940).
- **Shaders: GLSLC outputs in `.fxbnvn` files.** `NSW/SHADERS` holds 456 `.fxbnvn` files (161.7 MB, 56 bytes to 2.1 MB). Each starts with `FXB\0`, then its own length and a header length; inside are whole GLSLC outputs (magic `0x19866891`), each with one control section (`0x98761234`, 0x880 bytes) and its code area right after it. 7,720 outputs over all files (7,234 graphics, 486 compute), nothing compressed and no BNSH. 3-file banks of 56 bytes hold no shader. The survey's note ("no BNSH / BAHS at the top level … must be located first") does not count GLSLC outputs; `shader_split.py` reads them through its loose-file GLSLC path (`scan_whole` → `glslc_shaders`) with no new reader. `dm/tools/fxbnvn_probe.py` prints this structure from a `.nup` without writing game data.
- `shader_split.py` found 3,445 shaders: 244 compute, 1,757 pixel, 1,444 vertex, all from `nsw` (the 7,720 outputs repeat across banks). 5,776 variation pairs, 244 compute answer rows, no `[RED]` line. Single-stage programs: the 1,444 vertex shaders are paired with a cover of 4 pixel shaders.

- Modules: 0x5a00000 (90 MB) after the rewrite. With the default 64 MB of used memory, `main` asked for a 0xc9400000 heap (pool − 64 MB) and `SetHeapSize` refused it. With `mem_used 0x6000000` it asks for 0xc7500000 (3.11 GB). Not measured in play yet.

## Performance

Measured from the test app's logs (the `pace`, `[nvn] timing` and `longframe` lines; `DM_VK_GPUPROF=300` in the test app for this game), on the field in an exhibition, 1.0.19.

- **AYN Thor (Snapdragon 8 Gen 2), current.** About 34 fps (0.2.80, fast cores off and on alike). A frame is about 31 ms: the game's main thread runs 27–28 ms of CPU in it (guest waits 7–8 ms of that), the replay thread records in 12–13 ms, the GPU is busy about 18 ms, NVN submit and present about 0.1 ms. CPU-bound on the main thread; not thermal (headroom not reported, clocks at their caps).
- **Sony Xperia 1 V (Snapdragon 8 Gen 2), current.** About 18 fps with fast cores off, 20.6 on (0.2.80). Main thread about 50 ms of CPU a frame, GPU 36–45 ms, replay about 24 ms; thermal headroom 0 and CPU clocks capped (2.59 and 2.84 GHz), so it throttles. Scene pass 1440×810. Costliest GPU work: `PLAYERCOMPUTESHADERS` e0818838838d85df (14 dispatches, about 6.2 ms, a per-vertex collision loop of up to 500 iterations), `SKINNINGCOMPUTE` 7f78de8d31ad556c (about 6.3 ms), 212 draws of d214bad0d2a436d7 (5.4 ms).
- **The fastest core to the main thread instead of the replay thread (tried, reverted, 0.2.81).** Fast cores gave the busiest thread the 3.19 GHz core; that was the game's main thread. Its CPU time a frame did not drop (28.3 ms against 27.3 ms on a 2.8 GHz core) and the field fell to about 31 fps, so the replay thread keeps the fastest core (0.2.82). The main thread's time does not follow the core's clock: what it spends it on is open.
- **Retroid Pocket Duo (Adreno 722), current.** Drivers: Mr. Purple T30 (PurpleVK 26.3.0) draws best (player-reported glitches fewest); T23 and T26 make no Vulkan device; Turnip Gen8 V39 and Turnip Duo v5.1 show more flicker (menus, skin black and back). T30, 0.2.84: about 24 fps on the field, GPU p50 16.5 ms (24.5 on Turnip Gen8 V39), replay 17 ms, frame work about 38 ms; thermal status 3. Errors only the crowd shader skip and the texture ID past the table (as on the Thor); the flicker leaves nothing in the log.
- **Main thread inside NVN calls (0.2.84, RP Duo, T30).** About 12–13 ms of the 38 ms frame (`DM_NVN_PROF`). The largest are waits for the GPU: `SyncWait` about 4–5 ms and `EventGetValue` (the game polling an event) about 4 ms a frame; then trivial getters (`CommandBufferIsRecording`, `MemoryPoolGetBufferAddress`, `DeviceGetSeparateTextureHandle`) at about 2 ms together, much of it the timing wrapper's own cost. Submit 0.2 ms.
- **Crowd control (0.2.86).** The profile's `crowd` row lists the 19 `CROWDSHADER` vertex shaders; Game settings › Crowd control hides their draws (`DM_VK_SKIP_VS`). They are about 15 % of the field's GPU time (5.4 of 37 ms on the Xperia, 2.5 of 18 on the Thor, 2.4 of 15.5 on the RP Duo with T30) and 320–410 draws a frame. The game's own crowd work on the main thread stays. Measured (Thor, Turnip Gen8 V39, 0.2.90 against 0.2.84, exhibition on the field): 33.6 → about 52 fps; GPU busy 19.5 → 14.0 ms; replay recording 12.0 → 6.8 ms; main thread frame work 27.2 → 19.0 ms, of it inside NVN calls 10.9 → 6.7 ms, `SyncWait` and `EventGetValue` polling out of the top five. Far more than the crowd's GPU share: its draws sat in the replay-to-GPU chain the main thread waits on (below).
- **The main thread waits on the previous frame (current finding, 0.2.84 logs).** On the Thor the time from the replay's start to the GPU's end is 30–32 ms, about the whole frame (30 fps), while the replay records 13–17 ms and the GPU is busy 18–20 ms. On the RP Duo about 8–9 ms of the main thread's frame is `SyncWait` and polling `EventGetValue`. GPU events and syncs land only when the whole submission's fence completes (`vka_exec.c` completion effects), so the game's wait lasts until replay and GPU are both done. Polling counts as CPU time, which would explain why the faster core did not shorten the main thread. 0.2.90's `DM_VK_SYNCLOG=400` logged nothing: the game's waits do not block in `mtl_wait` (it polls). With the crowd hidden, the Thor's replay start to GPU end is 17–19 ms against a 6.8 ms recording and 14 ms GPU, so the GPU barely runs while the frame is recorded (parts every 600 draws: about 3 queue submits a frame). 0.2.92 tries `DM_VK_CHUNK=150` and `DM_VK_CHUNK_PASS=300` in the test app for this game, so the GPU starts sooner, and drops `DM_NVN_PROF` (its wrapper costs main-thread time on every NVN call).
- **Open: what the main thread spends its time on.** The test app sets `DM_NVN_PROF=1` for this game (0.2.82; it took effect only from 0.2.84, once the host armed it at the first `nvnBootstrapLoader` instead of in a constructor that runs before the launcher sets the environment), so the log splits the NVN calls' share (the `[nvn] translation layer top 5` line) from the game's own code.

## Found on this game

Boot and first frames:

- **Heap sized from the application pool less used memory (resolved).** First boot on an AYN Thor: `[mem] SetHeapSize 0xc9400000 + modules 0x5a00000 > app pool 0xcd500000`, then `nn::diag abort: Result 0x1003` at `main+0x5b1b60` in `nninitStartup`. Fixed by `mem_used 0x6000000`. [Heap sized from the application pool less used memory](../../../docs/reference/memory.md#heap-sized-from-the-application-pool-less-used-memory)
- **Opening video: nsd (resolved).** At `ATT_SCREEN: FMV player init` the game aborted (`Result 0xe8d`, `sdk+0x3f4cfc`) in `nn::nsd::GetApplicationServerEnvironmentType`, reached through `nn::oe::GetServerEnvironmentType`. The host answers that import with retail 0 (`hle_offline.c`).
- **Voice chat AudioOut used before it is opened (resolved).** COnline asks the headset output's channel count (`main+0x18cd30c`, `main+0x18cd674`) before the headset thread opens it; the host answers as for a closed output (`hle_audio.c`, `ao_or_closed`).
- **ContainsAudioOutBuffer (resolved).** A null read at `sdk+0x1e7e24` right after `audio #2 Start`: the host takes over `nn::audio::ContainsAudioOutBuffer`.
- **3D scene black: 119 textures in one bind (resolved).** The host refused binds of more than 32 texture handles whole; they are recorded in parts of 32 (`hle_nvn.c`, `bind_handles`).
- **Spikes, missing skin (resolved).** `SKINNINGCOMPUTE` and `PLAYERCOMPUTESHADERS` write storage buffer textures at offsets off the device's texel buffer alignment (64); such a binding is copied into aligned scratch memory before the dispatch and back after it (`vka_draw.c` tbuf_view, tbuf_writeback).

Generated players (create-a-player, Road to the Show). The whole investigation, with its wrong turns and the tools that found each cause, is in [docs/mlb-the-show-26-skin-and-hair.md](../../../docs/mlb-the-show-26-skin-and-hair.md):

- **The create-a-player model untextured (resolved, 0.2.20).** Its GPU-compressed textures (BC1/BC3/BC4/BC7, encoded by `TEXTURECOMPRESSBCN` compute through RG32UI and RGBA32UI views of the same storage) were all-zero blocks until the storage take covered compressed targets.
- **Generated faces black (resolved, 0.2.29).** The face's target skin tone comes from the CPU's read of the GPU-drawn skin tone palette (`CAP_SkinTonePalette`, 256x512 RGBA8; main+0x1688ae4 through `nvnTextureReadTexels`), which read the never-written storage. [`ReadTexels` of a texture the GPU wrote through another texture object](../../../docs/reference/nvn-objects.md#readtexels-of-a-texture-the-gpu-wrote-through-another-texture-object-vulkan-replay)
- **Hair tips and beards without colour (resolved, 0.2.30).** `HAIRCOMPUTE` 8cbd9b4be32e966d samples the BC1 hair albedo whose blocks were written through an RG32UI view; the storage take ran for draws only. [A compute dispatch samples a texture the GPU wrote through another format](../../../docs/reference/nvn-objects.md#a-compute-dispatch-samples-a-texture-the-gpu-wrote-through-another-format-vulkan-replay)
- **Body skin black on a loaded career (resolved, 1.0.24).** Compute 67d5da22e65373bf averages the skin tone palette into each body material's target tone (`ICE_SKINSHADER` fp_c4[2]); the palette's image had gone two frames after its texture object was finalized, and the later texture object over its storage got an empty image. [A GPU-drawn image goes before a later texture object over its storage reads it](../../../docs/reference/nvn-objects.md#a-gpu-drawn-image-goes-before-a-later-texture-object-over-its-storage-reads-it-vulkan-replay)
- **Frontend lighting (not a fault).** The menus' irradiance cube and light rig probe volumes are empty (0 lights: the bank points at the placeholder `nowhere` set); in a stadium the rigs hold hundreds of lights. The game's own state, not a host fault.

## Open

- **Hair in the player editor.** Some styles do not look right in the editor's close-up (reported after 1.0.24, not investigated yet). Hair colours were right in 0.2.30.
- **Real players black once.** In one session (an exhibition, Dodgers against Blue Jays, 1.0.22) every player's skin was black; the next exhibition was right. Not reproduced.
- **Background pipelines** are off by default for this game (`Prefs.psoAsync`, its own key `vk_pso_async2`): set off while chasing the black skin, which had another cause; the game has been played this way since. Whether it can be on again is not tested.
- A crowd shader skipped (more than 512 descriptors), one texture ID past the image table (66224), performance on Turnip: not looked at yet.
- SDK 19: NVN object sizes and service layouts differ by SDK; other SDK 19 profiles exist ([OCTOPATH TRAVELER 0](../01005270232F2000/README.md)).
